# 决策记录

本文件只记「已经定下来的事」，以及「还没定但必须定的事」。改任何数都改这里，不要靠翻聊天记录。

## 一句话

把 Qwen3.5-9B 的真实接线（φ）与真实权重（θ，取 Q4_K_M 量化版，见 D12）压成一根 25 × 25 × 80 mm K9 水晶柱里的立体雪花。
交付给厂家的是一份普通三维模型；爆点、点距、走刀全部由厂家决定。

## 五个词，不许混

| 词 | 含义 | 谁决定 |
|---|---|---|
| **体素** | 降采样后的灰度栅格；1 体素 = 该处 N 个权重的统计量 | 我们 |
| **点** | 体积里"有散射体"的位置。是雪花，**不是**激光爆点 | 我们，或 slicer |
| **爆点** | 激光在玻璃内部打出的微裂纹 | 厂家 |
| **几何** | OBJ 里的面与体 | 我们 |
| **灰度** | 0–255 的数值通道，slicer 可据此决定点的密度或大小 | 我们 |

## 已定

**D1 事实源只有一个：真实 checkpoint + `modeling_*.py` + 我们写死的降采样规则。**
IR、点集、OBJ、manifest 全部是派生物，可重算，**不允许手工编辑**。手工编辑派生物，追溯链就断了，作品就不再是拓片。

**D2 点数是后验结果，不是限额。**（用户 2026-11-16 拍板：纯后验核对）

三层分开，不能混：

| 层 | 是什么 | 由谁决定 |
|---|---|---|
| 网格 | 块里有多少个能放点的位置 = 块体积 ÷ 点距³ | 几何（块尺寸、机台点距） |
| 灰度 | 每个位置多亮、放不放点 | 数据（真实权重算出来的值） |
| 总点数 | 所有位置按灰度加权求和 | 上面两者相乘的结果 |

- 总点数**没有预设值，也没有可以“用完”的预算**。它只是算出来的。
- 后验报告（编辑器右上角）报：总点数、预计机时、可雕区平均填充率、块内平均填充率、最密一块的平均与局部峰值、每体素代表多少权重。
- **只报警，不改生成**。超过参考线就标红，提示去调 γ / 底噪地板 / 压缩倍数 / 毛坯，然后重新算一遍。参考线本身是报警阀值，不是配额；它的来源见 U12。
- 为什么看局部峰值而不是总平均：裂是局部现象。总平均 10 % 但某一小块实心到 60 % 照样可能裂。类比 3D 打印切片：报的是“最高处多少度、最大悬垂多少度”，不是总体积。
- 屏幕上画多少个点是渲染抽样，与玻璃里实际多少个点无关，两者在界面上分开标。
- **作废的旧表述**：`墨水预算 = 栅格 × 填充上限`、“雪花用掉剩余预算”。这两条等于先定总数再分配，与自适应生成矛盾，已从代码和本文中删除。

**D3 框和包络面都是实体，粗细（毫米）和灰度都可调。**（用户拍板）
- 框：每个块的 12 条棱各是一根方梁，截面边长就是"框的粗细"。
- 包络面：每个块外面一层闭合薄壳，壳厚就是"包络面的厚度"。
- 为什么必须是实体：零厚度的面片和 OBJ 里的 `l` 线段，在切片软件里基本切不出点；另外 WebGL 的线条宽度在 Windows 上恒为 1 像素，用线条画的框在预览里也调不了粗细。做成有毫米截面的实体后，预览里看到的粗细就是导出的粗细。
- "透明度"就是灰度：玻璃里没有透明度，只有点的疏密。框和壳各有一个灰度滑块，预览里显示为透明度，成品里是点密度，不单独做"透明度"滑块。
- 粗细的下限是 2 倍点距：0.08 mm 点距下，0.2 mm 只有 2.5 层点，切出来会断断续续。
- 点数量级估计（假设：约 300 个块，单块典型尺寸 1.2 × 4 × 4 mm，0.08 mm 点距；可雕区格数按 586 万算）：
  - 框：每块棱长合计 36.8 mm，300 块共 11,040 mm；截面 0.3 × 0.3 mm 时满密度约 194 万点（可雕区格数的 33 %），灰度 15 % 时约 29 万点（5 %）。
  - 壳：每块表面 51.2 mm²，壳厚 0.16 mm 时每块满密度约 1.6 万点，300 块约 480 万点（可雕区格数的 82 %），灰度 10 % 时约 48 万点（8 %）。
  - 所以框和壳可以做在每个块上，但**默认灰度必须低**，否则结构件自己就把局部密度拉得很高，数据再一亮就叠在一起。这是后验报告会直接告警的事，不是要预先扣掉一块配额。
- 本条旧版写的"框只做骨架级，模块之间靠黑缝分隔"是我当时的收缩建议，已被用户的决定取代。整块可雕区外面要不要再包一层大框，是另一个问题，见 U4。

**D4 谱分解要做。它能把一部分真实结构从底噪里分出来，但不是全部。**
做法：噪声上界用奇异值口径 `s₊ = σ(√m + √n)`（σ 是这张矩阵所有元素的均方根，m、n 是行数和列数；一张同尺寸、同 σ 的纯随机矩阵，最大奇异值大约就在这里）。用带 2 次幂迭代的随机化 SVD 求前 K 个奇异值，大于 s₊ 的算"结构方向"，个数记为 k；`W_struct` 是这 k 个方向重构出的矩阵，`W_res = W − W_struct` 是剩下的部分。
实测（脚本 `scripts/compare_spectral_pooling.py`，图 `out/fig/spectral_vs_pooling.png`；BF16 权重，池化到 100×100）：

| 张量 | s₊ | 前几个奇异值 | 界外 k | 结构能量占比 | 池化图 CV（纯噪声理论 CV） |
|---|---|---|---|---|---|
| L0 mlp.down_proj 4096×12288 | 1.918 | 7.18 / 2.65 / 2.55 / 2.48 … | ≥ 15 | 1.99 % | 1.53 %（1.06 %，1.4 倍） |
| L3 self_attn.q_proj 8192×4096 | 2.861 | 13.60 / 6.96 / 6.71 / 6.27 … | ≥ 32（碰到上限 K=32） | ≥ 7.86 % | 16.20 %（1.30 %，12.4 倍） |
| 同形状同 σ 的纯随机高斯 | 1.918 | 1.76 / 1.75 / … | 0 | 0 | 1.06 %（1.06 %，1.0 倍） |

CV 是池化图的标准差除以均值；"纯噪声理论 CV"是同样每个体素平均那么多个独立高斯数时应有的波动。随机化 SVD 估出的奇异值不会超过真值（投影只会让奇异值变小），所以表里的 k 和能量占比都是下界。

图里看到的三件事：
- down_proj 池化后唯一看得见的结构（底部一整行偏亮）落在 `W_struct` 里，在 `W_res` 里消失了。这一类结构，谱能分出来。
- q_proj 的横带在 `W_res` 里几乎原样还在。它们是"某些行整体偏大或偏小"，不是低秩方向，谱分不出来，要靠行 / 列范数。
- 纯随机矩阵在谱上什么都没有，池化图在固定标尺下是一片均匀灰，这就是"实心雪花块"的样子。down_proj 的池化 CV 只有纯噪声的 1.4 倍，整体接近它；q_proj 是 12.4 倍，远离它。

**更正**：本条旧版写的"前 8 个奇异值 3.39 / 1.466 / …，只有第 0 个在界外，谱切不出有内容的图"是错的。当时 `scripts/test_quant_visibility.py` 的 step 6 用的随机化 SVD 没有做幂迭代，对衰减慢的谱严重低估（3.39 的真值至少是 7.18）。以这组数为前提的结论作废。

**D5 三个时间尺度必须分开。**
- 小时级：读权重 + 降采样（每模型一次，结果缓存）
- 秒级：重采样 + 重布局 + 重导出（每次改参数）
- 毫秒级：转视角、拖外观滑块

**改完参数后绝不重新读权重。** 这是"微调循环 ≤ 5 秒"的唯一保证。

**D6 前端单文件 HTML + CDN three.js r128；后端是 Python CLI（uv + numpy + gguf）。**
不引入 node + 不引入打包器：本机没有 node，且 r160 之后 `build/three.min.js` 与 `examples/js/` 已被删除，踩过两次。r128 自带的 `OrbitControls.js` 与 `TransformControls.js`（用作 gumball）已确认在 CDN 上可取。
不引入 torch：只用到 numpy 的矩阵乘，不需要 2.5 GB 的运行时。
`gguf` 是 llama.cpp 官方的 Python 包（已确认 0.19.0 版自带 `quants.dequantize`，支持 Q4_K 与 Q6_K），用来把 Q4 文件里的 4 bit 编码解码成数值，见 D12。

**D7 预览必须吃"最终会导出的那份点集"，不能另起一个生成器。**
否则预览会骗人：alpha 混合看起来像雾，玻璃里只有点的数量。

**D8 结构用几何，数据用灰度；几何件也带灰度，用灰度控制它们占多少点。**
框、壳、残差棒是结构，形状来自布局；块内的雪花是数据，灰度来自权重。
两类东西共用同一个点数预算。几何件的点数由它的体积 × 灰度决定，在用量表里单独列出；它们的默认灰度要低，把大部分点留给雪花（估算见 D3）。
如果导出走的是"几何 + 灰度贴图"路线（U1 乙），切片软件是否读灰度尚未验证，几何件实际切出多少点要靠测试件确认（U2）。

**D9 参数分三类，不许混在一个滑块里。**
- 外观：只影响屏幕，不进文件。相机、标签开关、"按功能着色"开关、设计视图 / 成品模拟视图切换。
- 几何：改变导出的形状，进 manifest。毛坯、模型的缩放 / 旋转 / 平移（gumball）、框截面、壳厚、棒径、层间隙、压缩倍数。
- 数据：改变点的数量或位置，进 manifest。γ、p_floor、U7 的合成权重、谱分解的 K、框 / 壳 / 棒的灰度、填充上限。
注意：本条旧版把"线框透明度"归为外观。现在框是实体，它的透明度就是灰度，会变成玻璃里的点，所以归为数据。

**D10 区分主次不能只靠一种统计：谱结构与行 / 列范数都要用。**
理由见 D4 的实测：down_proj 那一行亮带是低秩方向，谱能分出来；q_proj 的横带是整行缩放，只有行范数能分出来。两种结构都真实存在，各自只有一种统计看得见。
底噪地板（`W_res` 的池化 + p_floor）保证块内不真空，但不能高到把块填成实心。
三部分怎么合成、默认权重多少，还没定，见 U7。
本条旧版（"压噪基于局部统计，不基于谱能量"）建立在 D4 旧版的错误奇异值上，已作废。

**D11 视觉语法：以 `prototype/real_config.html` 的审美为底，切片布局 + 残差棒。**（用户拍板）
- real_config 的审美：黑底白点、每层一片、片内模块并排、块与块不碰撞、铭牌、视觉塔可开关。
- 残差棒：用一根从 embed 贯穿到 lm_head 的细棒表示残差流。残差流就是代码 `x = x + attn(norm(x)); x = x + mlp(norm(x))` 里的那个 x：每个 token 一个 4096 维向量，32 层轮流通过 norm 读一份、算出修正、再用 `+` 加回去。残差连接本身是标准结构（ResNet 2015、Transformer 2017 起所有主流模型都有），"把它画成一根棒"是本项目的设计选择。
- 棒没有权重，是纯几何，表达的是 φ（接线）。它是全作品唯一没有权重来源的实体，manifest 里要写明它来自代码。
- 棒粗细恒定，因为 x 在 32 层里始终是 4096 维。默认 1.2 mm 方棒，满密度约 17 万点，占预算 3 %。

**D12 权重来源：Qwen3.5-9B 的 Q4_K_M 量化版 GGUF。**（用户拍板，不追求原精度）
- 依据：U5 的实测，池化到体素尺度后 Q4 与 BF16 的差异在打点本身的随机波动以下。
- Q4_K_M 是一套混合配方的名字，不是每个张量都是 4 bit。实测这个文件用了 5 种格式：Q4_K（132 个）、Q6_K（22 个，含 lm_head 和一半的 ffn_down）、Q5_K（48 个）、Q8_0（48 个）、F32（177 个一维张量等）。每个张量的实际格式都要记进 manifest，铭牌上写 `Qwen3.5-9B · Q4_K_M`。明细见 `docs/qwen35_9b_facts.md` 第 3 节。
- "反量化"在这里只是解码：Q4 文件里每个权重存的是一个 0–15 的整数编号，再配一组每块共用的缩放系数；只有乘回去才得到能算 |w| 和 SVD 的数。解码出来的就是 Q4 的值，不会恢复 BF16 精度。
- GGUF 里的张量名与 HF safetensors 不同，对照表见 `docs/qwen35_9b_facts.md` 第 4 节。已用真实解码与 HF BF16 逐元素比对确认名字对应、维度方向、解码都正确（Q4_K 的 q_proj 相关系数 0.9973、误差 7.4 %；Q6_K 的 down_proj 相关系数 0.99983、误差 1.8 %）。
- GGUF 版**没有 MTP 头**（按张量数对账推出），见 U9。
- GGUF 与 HF 有三处数值约定不同：norm 权重加了 1；A_log 换成了 −exp(A_log)；线性注意力的 32 个 value 头被重新排序。见 U10。
- 文件（已选定）：`unsloth/Qwen3.5-9B-GGUF` 的 `Qwen3.5-9B-Q4_K_M.gguf`（5.68 GB，文本部分）与 `mmproj-BF16.gguf`（0.92 GB，视觉塔），下载到 `data/gguf/`，用 HF 记录的 sha256 校验（`scripts/download_gguf.py`）。同仓库还有 BF16 版，以后要对照时命名一致。备选来源：`lmstudio-community`（5.63 GB）、`bartowski`（6.17 GB）。
- 精度是混合的：文本部分是上面说的 5 种格式混合，视觉塔是 BF16。manifest 按张量记录。视觉塔是否进作品仍见 U3。

**D13 二维张量放进三维块的方式：注意力按头拆，MLP 与 embedding 按块的长宽比拆。**（用户拍板）
为什么要拆：权重在文件里是二维数表，每个数只有"第几行、第几列"两个坐标；玻璃里的块是三维的，每个位置需要三个坐标。把数表的一个轴拆成两个，就得到第三个坐标，每个数在块里恰好出现一次。
- 注意力（有结构依据）：把由"头数 × 每头维度"组成的那个轴拆开。
  - 全注意力层：`attn_q` 的 8192 行 = 16 个头 × 512（512 里一半是 Q、一半推断是输出门控，未核对代码），整张表变成 16 × 512 × 4096 的立方体。`attn_k` / `attn_v` 是 4 个 KV 头 × 256，`attn_output` 拆列（16 × 256）。
  - 线性注意力层（已由 GGUF 元数据与形状确认）：`attn_qkv` 的 8192 行是三段拼起来的——q 2048 行（16 个 key 头 × 128）、k 2048 行（16 × 128）、v 4096 行（32 个 value 头 × 128），先按段分开再按头拆。`attn_gate` 拆行（32 × 128），`ssm_out` 拆列（32 × 128），`ssm_alpha` / `ssm_beta` 本来就是每个 value 头一行。这些张量里 value 头的顺序被 llama.cpp 重排过，见 U10。
  - `attn_qkv` 的三段要不要画成三个子块，留到布局阶段定。
- MLP 与 embedding / lm_head（几何选择）：把长的那个轴（MLP 的 12288 个神经元、词表的 248320 个 token）分解成两个因子，因子按块的长宽比选。MLP 神经元的先后顺序本身没有含义（打乱顺序模型的计算结果不变），所以这一步不是结构依据。
- 一维张量（norm 的 γ、`A_log`、`dt_bias` 等）：没有谱，只做池化；把长度因式分解成小块。本来就是三维的张量（如 `conv1d`）按原形状。
- 不沿深度复制同一份数据：那样看起来也是三维，但同一个数会出现多次。
- 每个张量的原始形状、拆分因子、哪个轴对应块的哪个方向，都写进 manifest。
- 已知的巧合：real_config 布局里每层块的厚度约 1.2 mm，0.08 mm 点距下约 15 层格子，和 16 个头接近，可以考虑一个头占一层。未定，留到布局阶段看效果。

**D14 编辑器的可调项。**（用户拍板的功能清单；先做 Qwen3.5-9B 的具体实例，再逐步改成读模型文件的通用工具）

| 可调项 | 怎么实现 | 备注 |
|---|---|---|
| 框的粗细和灰度 | 方梁截面（mm）+ 灰度 | 见 D3 |
| 包络面的厚度和灰度 | 薄壳厚度（mm）+ 灰度 | 见 D3 |
| 残差棒 | 棒径（mm）+ 灰度 | 见 D11 |
| 机器加工分辨率 | 点距 + 点径，存成一份机台参数 | 改它会改体素栅格和点数预算 |
| 底噪滤波 | 底噪地板 + γ + U7 的合成权重 | 底噪太高会实心，太低会空 |
| 降采样压缩力度 | 数据格子边长 = 压缩倍数 × 点距 | 1 倍表示每格对应一个可打点的位置 |
| 毛坯选型 | 预设几种尺寸 + 自定义；画出毛坯框和可雕区 | |
| 模型缩放 / 旋转 / 平移 | gumball（three.js r128 的 TransformControls） | 几何参数，进 manifest |
| 成品模拟视图 | 按点距把灰度转成真实数量的白点，按真实点径画 | 见下 |

必须同时有的：
- **点数用量表**：分项显示框、壳、棒、雪花各用多少点，合计占预算多少，以及预计机时。
- **悬停显示身份**：指到一个块，显示它来自哪个张量、原始形状、量化类型、每个体素代表多少个权重、谱分解的界外方向数。
- **"按功能着色"开关**：只影响预览，默认关，导出永远不带颜色（玻璃里的点永远是白的）。

三个参数是联动的：压缩倍数、模型缩放、点距，定下两个，"每个体素代表多少个权重"就定了：
`每体素权重数 = 张量权重数 ÷ (块体积 ÷ 数据格子体积)`，`数据格子边长 = 压缩倍数 × 点距`，`块体积 ∝ 缩放³`。
所以这三个是自由滑块，"每体素权重数"只显示、不给滑块。
它们都会改变池化尺寸。为了遵守 D5（改参数不重读权重），第一次读权重时给每个张量存一份足够细的中间统计（按 D13 折叠后的三维网格，含均值、RMS、谱结构部分、剩余部分、行 / 列范数），之后拖滑块只从这份中间结果重新池化。中间网格多细、占多少空间，在阶段 2 实测后定。

成品模拟视图能模拟什么：走刀顺序（先打哪个点）在成品上看不出来，看得出来的是点最终落在哪、有多密。这个视图模拟的是"我们给出的灰度，被厂家切片软件用误差扩散一类算法转成点之后的样子"。它是近似，不是厂家的真实输出；最终校准靠 U1 / U2 的测试件。507 万个点在桌面浏览器里一般画得动，待实测；手机上可能需要抽样显示。

### 阶段 1 现状

实现上的分工（agent 的实现选择，可推翻）：
- **拓扑在 Python 里生成**：`scripts/build_topology_qwen35.py` 读阶段 0 的张量清单，按 D11 / D13 把每个张量分到功能块，写出 `prototype/data/qwen35_9b.topo.json`。内置两条硬检查：引用的张量必须存在；清单里每个张量必须恰好归入一个块。不通过就报错，不出文件。当前结果：403 个块（文本 347、视觉 56）+ 2 个纯几何件，文本 427/427、视觉 334/334 个张量全部归入，参数总数与清单一致。
- **拓扑文件放在 `prototype/data/` 下**（派生物，只此一份，由脚本覆盖改写，不手改）。放这里是因为前端没有构建步骤，只能用相对路径读：放同目录才能让“服务根是 `prototype/`”和“服务根是项目根”两种起法都打开，不必记住端口。
- **布局只在前端实现一次**：`prototype/snowglass_editor.html` 里的 `layout()`。理由是框的粗细、毛坯、缩放这些滑块要即时生效。导出时由编辑器写出 `layout.json`（参数 + 每个实体的毫米包围盒 + 检查结果），交给后续步骤，布局逻辑不在 Python 里再写一遍。
- 本地服务：`prototype/` 下任意一个 http 服务都行，例如项目根跑 `python -m http.server 8124` 后打开 `http://127.0.0.1:8124/prototype/snowglass_editor.html`，或 `prototype/` 里跑 `python -m http.server 8123` 后打开 `http://127.0.0.1:8123/snowglass_editor.html`。直接双击 html 文件不行（浏览器会拦 fetch）。

布局规则（第二版，照 `prototype/real_config.html` 的排法，待目测）：
- **竖直**：从下往上 embed → 32 层塔体 → final norm（脖子）→ lm_head（右侧跟一个小 MTP 框）。头高 5.5 mm、离塔端 2.6 mm 空隙；脖子居中、扁 1.25 mm、离塔顶 1.6 mm。层距由可雕区高度反算（32 层填满剩余高度），块高占层距的 76 %（剩下的是空气）。
- **水平**：从左往右 = norm 柱 | 主体 | 空隙 | 视觉塔，比例照 6.8 : 3.7 : 3.4 映射到可雕区宽度。
- **每层**：两侧都从主体外边缘往里排，**两条 norm 柱在最外侧**（与 real_config 一致），每条列的子块从外往内按张量顺序。
- **深度错开**：注意力列在 z = −2 mm，MLP 列在 z = +2 mm，即前后错开 4 mm。**块的深度不切**（仍等于可雕区深度），所以总深度超出可雕区 1.6 mm；这是故意的，靠 gumball 缩放收。
- **残差棒**：留在两列之间的中线上，贯穿塔体，在两列之间的 x 缝里，不占额外空间。
- **视觉塔**：独立一列，与主体隔 3 mm，宽 3.4 mm，只占塔体高度的 2 %–62 %（下半截）；patch 嵌入在底，往上流到顶部的投影器。
- **初始缩放 0.9**，不顶头。报告里的“按可雕区适配缩放”会算出精确值（当前建议 0.93）。

已验证（浏览器 DOM）：页面无报错，405 个实体两两不重叠，包围盒 17.7 × 21.6 × 67.5 mm。未验证：画面本身（自动化环境的浏览器面板不可见，截不了图）。

### 阶段 2 现状（真实权重第一轮）

脚本：`scripts/try_one_block.py`（解码 → 池化 → 谱分解 → 灰度 → 出图）、`scripts/compare_quant_visual.py`（BF16 与量化版的池化图逐格对比）。输出在 `out/fig/`、`out/blocks/`。

**1. 量化对可视化的影响：没有。** 同一张量分别用缓存的 BF16 原版和 GGUF 量化版池化到同一网格，逐格相关系数：L0 ffn_down（Q6_K）0.99970（|W|）/ 0.99983（signed）；L3 attn_q（Q4_K）0.99963 / 0.99824。两者 CV 在小数点后三位完全相同。原因：每格平均 300–500 个权重，量化误差在池化时被平均掉了。这给之前 U5 的问题（量化版看不出区别吧）补上了池化尺度的证据。

**2. 不同块的结构强度差很远。** 池化到 418 × 250 格（与块的 19 × 22 × 250 网格同形，每格 300–500 个权重）：

| 块 | 格式 | abs 池化 CV | 纯噪声 CV | 比值 | 谱分解界外 k | 结构能量 | 行范数 max/中位 | 列范数 max/中位 |
|---|---|---|---|---|---|---|---|---|
| L0 ffn_down | Q6_K | 0.041 | 0.034 | 1.2 | 1 | 1.6 % | 2.06 | 1.01 |
| L3 attn_q | Q4_K | 0.184 | 0.042 | 4.4 | 7 | 32.9 % | 1.45 | 1.07 |
| L0 attn_qkv | Q5_K | 0.112 | 0.042 | 2.7 | 7 | 16.9 % | 1.42 | 1.03 |

> "纯噪声 CV"指同格子数、同均值的随机数组，每格 n 个样本取均值后的 CV = 0.5708/√n。表中的 CV 都是对 abs（绝对值）池化图算的。

**3. 谱分解不是万能的。** 在 attn 类块上它有 7 个界外奇异方向（能量 17–33 %）；在 ffn_down 上只有 1 个，而且就是全图均值（把非负的 |w| 图做谱分解，常数项必然是最大方向）。另外，signed 池化图的逐格均值与纯噪声的比值几乎正好是 1（0.0457 对 0.0456），说明和/列方向的逐格均值里没有低秩结构。

**4. 这些块的变化主要在"行"，不在"列"。** 三个块的行范数 max/中位都是 1.4–2.1，列范数都是 1.01–1.07。换成布局的语言：块的长轴（z，20 mm）对应列方向，而列方向几乎是平的；横带都在 (x, y) 平面上。

**5. attn_q 的横带是真的，不是量化造成的。** BF16 和 Q4_K 的池化图肉眼几乎无法区分，差值图是均匀噪声。横带间距量级与 8192 行 / 418 组的 8 个头分组有关，具体对应关系未核对。

**阶段 2 待定。**
- 灰度主源用什么：目前测了五种（|w| 均值、signed 均值、行范数×列范数、|w| 减外积的残差、前两种合成）。signed 是纯噪声；外积太光滑，会把横带抹掉；|w| 均值最直接可读。倾向用 |w| 均值，但未拍板。
- 块的网格尺寸：试算时借用 19 × 22 × 250（即 L28.v 那个块的格子数），ffn_down / attn_q 的实际块宽不同，要对齐得先拿到编辑器导出的 `layout.json`。
